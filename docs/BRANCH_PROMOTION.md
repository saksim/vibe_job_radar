## 开发与验证

1. 从最新 dev 创建功能分支，将对应 Issue、具体行为改动、定向验证和剩余问题写入 PR。
2. 功能 PR 合入 dev 后，建立 dev → release PR。冻结本批范围；后续修复仍经功能分支 → dev，再进入 release。
3. release → main PR 验证同一批交付，使用普通 merge 保留晋升历史。不能直接把功能分支或 dev 合到 main。
4. 每轮结束后，将后续开发基线同步到 main，保留独立提交。不要对仍在使用的远端分支盲目强推。

已有全部 PR 验证和 main 验证保留。dev/release 不额外增加 push 全套，避免每次合并重复触发同一阶段的全套任务。本机只运行本次改动相关检查；CI已有构建直接用于发行，不另建包。

`promotion-policy / promotion-route` 检查 PR 的来源仓库与分支顺序，并检查晋升说明完整性。它是仓库检查；是否作为 GitHub 必需检查取决于仓库保护规则，不声称已经设置保护或禁止管理员绕过。

## 每次晋升和发行说明

晋升 PR 与发行草稿都应提供这四段实际内容，并关联 Issue/PR：

- `## 解决了什么`：用户触发条件、原问题与现在的行为。
- `## 提高了什么`：可核对的能力或实际指标；未量化的改善不编造数字。
- `## 验证结果`：对应提交和实际执行结果；待完成 CI 明确写待完成。
- `## 剩余问题`：依赖、已知限制、未完成验收；没有时明确写无已知剩余问题。

发行脚本通过 `--change-notes` 读取已审查说明；创建草稿时必填。说明进入草稿正文、`CHANGES.md`、校验清单和来源摘要。旧下载包、旧草稿及原工作区不会被覆盖。
