# robots 文件不存在时继续已适配的正常访问

2026-09-23 公开观察中，猎聘搜索 API 和认证 API 的 `/robots.txt` 返回 404。此前原生浏览器将任何非 200 都报为 `robots_unavailable`，因此在访问页面前就停止，已适配的正常登录和只读搜索请求也无法继续。

两个引导采集浏览器后端现在统一使用同一个规则解析器：

| 返回结果 | 处理 |
| --- | --- |
| 404 / 410 | 当前来源没有 robots 文件；继续检查已有域名、操作、认证状态和配额约束 |
| 200、可解析的文本规则 | 按 User-agent、最长匹配、Allow 同长优先、`*` / `$`、百分号编码判定；保留 Crawl-delay / Request-rate |
| 401 / 403 / 429 | 仍停止；真实请求保留原错误及冷却时间 |
| 5xx、网络/TLS 错误、未处理的重定向 | 仍停止，不能当成文件不存在 |
| 200 返回 HTML、非法编码、空正文或超限规则 | 仍报告规则不可确认 |

依据：[RFC 9309 §2.3.1.3](https://www.rfc-editor.org/rfc/rfc9309.html#section-2.3.1.3) 允许在 robots 返回 4xx 时继续访问。本实现只区分明确的 404/410，没有把认证拒绝、限流和其他 4xx 统一放行。该 RFC 同时明确 robots 不是访问授权机制；文件不存在也不会扩大程序已有的请求契约。

原生浏览器读取 robots 时，对这个控制文档附加禁用脚本、子资源和表单的 CSP，保留上游状态、原始解码正文及已有策略。404 的 HTML 错误页不能在规则确认前执行脚本。没有追加上游请求，也没有将 404 改写成 200。诊断只记录 `robots_file_absent`，不记录正文或凭据。

HTTP 桥此前使用的标准库解析器不能正确解释 `*` / `$`。与原生后端统一后，明确禁止的查询路径在两个后端都会停止。后续 #85 将同一[规则匹配器](SHARED_ROBOTS_RULES.md)共享给高级HTTP `SiteFetcher`，保留它原来的404/410停止边界，避免换入口后决定不同。

真实原生浏览器检查已使用本机之前保存的网络偏好，加载主站、搜索 API、认证 API 三个来源的 robots，越过原 404 阻塞。随后定位到首页的 `common-footer` iframe（`wow.liepin.com/t1009027/index.html`）导致整页中止。原生 CORS 文档现在在加载前禁用未支持的子框架，保持主文档和表单可用，不扩大域名范围；嵌入式登录仍未宣称支持。另外修复导航瞬间没有 `body` 时过早判为登录失败的问题，在原有 15 秒总期限内等待，不重新导航或提交。

## 验证与剩余工作

`tests/test_guided_robots_status.py` 验证来源隔离、既有操作边界、允许的详情路径、禁止的查询、错误分类、单次规则读取和已有速率约束不被重置。原生文档测试验证 404 状态和正文保持、附加禁用脚本的策略。现有原生浏览器 CI 的人工 API 来源改为 HTML 404，继续验证真实浏览器的 CORS 搜索、完整正文入库及报告链路。

这解决的是 API 来源的 robots 404 阻塞，**不是实站完整取数完成**。猎聘主站公开规则中的 `Disallow: /*?*` 仍阻止带查询参数的搜索入口。真实账号登录、当前完整请求依赖、首个完整真实 JD 仍需单独验收；不关闭 #45/#49/#50。
