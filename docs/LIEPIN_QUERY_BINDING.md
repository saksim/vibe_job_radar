# 猎聘正常表单的请求配对

正常表单先修改同页URL，再由站点脚本发送搜索请求。直接把所有URL字段与正文主条件同名比较，会拒绝发布方自己的日期、薪资及交互字段转换。旧代码用虚构值组成的完整官网结构已实际复现`liepin_search_query_mismatch`；这是离线兼容性缺陷，尚不能证明真实关键词提交已成功。

依据是之前保存的官网搜索脚本（SHA256 `2a6f29513fa80ba50bbc1cc14e4a05da1823d0853da53563f593186b30516ec0`）与URL序列化公共脚本（SHA256 `865b29d63791601dbfd17e6f5186bf235d20a1fc7326e8b36007b42ec5aa9f75`）。本次只读取代码和使用虚构测试值，没有执行第三方脚本或构造业务请求。

配对逐项保留真实约束：

- 关键词、地区、公司、行业、经验、学历、其他已知筛选和分页仍须对应；补入官网的`salaryCode`及`suggestTag`。未知字段、重复URL参数、重复JSON键、冲突或悄悄增加的非空筛选均拒绝。
- URL的`pubTime`映射到`hrActiveTimeCode`；兼容旧同名形状时，存在的两个字段都必须相等。不能以别名隐藏冲突日期。
- `salaryCode`包含一个`$`时，正文代码清空并将两段分别写入`salaryLow`与`salaryHigh`；其他代码保持且边界为空。每段逐一配对，不能丢掉上下界或多余分隔符。
- `scene`、`skId`、`fkId`与正文`passThroughForm`逐项相等；`ckId`按官网流程在URL更新后生成新值，因此两端分别验证32位小写base36形状，不要求相等。
- URL的`suggest=null`只对应无建议，不能夹带非空`suggestId`。对象序列化值本身不算身份：只接受含唯一`suggestId`的对象，并与URL标识精确匹配。

每个响应仍绑定完整实际URL的摘要、页码和请求序列；交互标识变化不能取用旧响应或旧DOM。分页范围只排除明确属于交互信息的`scene/skId/fkId/ckId`，所有实际筛选与建议标识继续冻结；首个页面也不能覆盖用户显式条件。不记录账号、正文负载、搜索值或交互标识原值。

登录返回观察器对原生猎聘结果使用同一查询范围规则：仅在任务启用查询范围版本1、原搜索地址一致且快照要求业务响应时接纳官网补入的默认参数。观察期间使用状态副本，不提前冻结或修改任务筛选；首次捕获仍由正常收集流程保存。显式筛选、已冻结条件、关键词、页码必须匹配，条件变化即使职位ID不变也需重新取得两次稳定观察。只有明确的交互元数据轮换不影响稳定性，每次结果仍须绑定自己的完整当前URL。普通DOM/旧任务保留原精确URL参数比较。

查询范围修正只将已返回的原搜索列表排入一次捕获，不提交登录或判定账号认证成功。无关键词入口另按[登录入口接续条件](LOGIN_SEARCH_ENTRY.md)在用户本次授权、账号区域及搜索控件稳定可见时提交原关键词一次；不能用默认推荐或仅有搜索框触发。真实账号、会话恢复、实际招聘站结果仍需各自证据；旧CI和入口失败不能用这些测试改写。没有新的API或站点权限，robots/TLS/共享限额保持。
