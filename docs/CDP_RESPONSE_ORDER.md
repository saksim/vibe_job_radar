# CDP回复与延后事件顺序

`0892b78` 首次21/21通过后，2026-09-25 16:33 UTC唯一实站在入口39.922秒出现page_not_ready，最终DOM也无法读取。没有native fatal、输入或配置请求，未记录跳白；不能认为配置已在实站验证，也没有足够证据确定这个实站失败的底层原因。

排查中发现一个可独立复现的命令等待问题：处理早到的请求事件时，回调需要等待自己的CDP回复；这段期间连接可能已经收到外层命令的回复，以及在该回复之后到达的更多事件。原实现要求整个延后队列清空才返回外层回复，后来事件的处理又能产生更多事件。这样一个已经及时获得回复的命令仍可能因为后续事件而超时。

连接现在记录收到消息的本地顺序。外层命令返回前仍处理回复之前的事件，包括导航和会话退出；回复之后的事件留在原有有界FIFO，供接下来的命令或事件泵按原顺序处理，不丢弃、不提前放行网络请求。后续DOM读取观察到导航仍抛PageSnapshotChanged。没有提高命令期限、32个待答命令上限、512个事件上限或字节限制，旧截止时间和错误检查保持。

新增本地用例在旧实现先复现native_protocol_error，覆盖回复后的工作不再拖延已完成命令、后续FIFO处理、回复前工作仍可超时、协议错误不泄漏消息、下一命令与导航保护及清理。原80并发事件、回复前导航/会话退出等测试继续保留。这个修复与实站page_not_ready的因果关系仍须新的实际证据，不能将本地复现当成已解决猎聘搜索。
