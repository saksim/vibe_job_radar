# 同工作区公开任务所有权

跟踪 #89，承接 #68/#30 H4/#9 R3-R4，基于待审 #88 的每日计划。不是已合并 main 或跨设备配额完成声明。

## 问题与修复

旧代码只知道本实例的线程。两个工作台同时使用同一工作区时，第二实例会把第一项仍运行的任务误标为中断，并接受新任务覆盖 `public_tasks/state.json`。人工复现中第二次来源请求被已有工作区锁阻止，所以不能把问题说成底层锁失效；真实缺陷是任务状态、提交、取消和恢复的所有权错位。

现在公开任务提交前取得 OS 文件锁，直到后台任务完成并保存终态才释放。锁被占用时返回 `public_task_busy`/HTTP 409，不修改任务ID、不覆盖原记录、不启动第二线程。进程退出时 OS 释放锁，不通过 PID 或锁文件年龄猜测是否存活。

另一个工作台仍能读当前任务和最终报告，但运行时显示“另一个本机服务正在执行”，隐藏不能控制的停止/继续按钮，禁用重复提交。关闭这个查看进度的实例不会取消真正所有者的任务。需要停止时回到原工作台；所有者取消后，其他实例可以明确确认继续同一个已保存查询。

真正进程退出后，上次运行记录成为可确认的中断；不会自动联网。恢复在取得所有权后再次读取磁盘记录，阻止旧页面在竞争窗口恢复已被替换的任务。原 ID、查询、绑定、尝试次数、缓存与来源配额保持。线程创建或初始写入失败也释放锁，未启动的线程不会在服务关闭时被错误 join。

状态读写共用一个短期文件锁，避免 Windows 读取句柄阻止原子替换；短锁最多等待5秒，长期所有权锁始终不阻塞。只读返回的所有权/控制标记不写入原任务文件。

#102补充同进程内按工作区规范路径的公平排队。#100的Windows/Python3.10回归曾出现连续60次保存使观察线程等待短锁超时；不能把其他分支偶然通过当作不会饥饿。等候者现在先排队，再由队首争取原OS锁；下一次写入不能抢到已经排队的观察者前面。超时/异常清除票据，不增加5秒上限，不串行其他目录，不改变跨进程任务所有权或进程退出释放。公平顺序只保证同进程调用者，跨进程重试仍可能有界失败。

## 与每日计划配合

到期计划遇到其他实例的公开任务时等待，保持原计划。若在检查与提交之间被另一实例抢先取得锁，明确的“未提交”busy返回等待，不当作已发请求重试。调度器交接遇到仍有所有者的匹配任务时等待结果，不误判进程已死；后续按原ID对账保存报告。

另一实例可以停用未来计划，但不越权取消其他实例拥有的当前任务。正常持有调度锁的实例会读取停用状态并请求取消自己的任务；若任务仍归正在退出的服务，等待其原关闭/只读步骤完成。原报告和缓存仍保留。

## 实际验证

新增12项测试覆盖双实例状态、重复提交与取消、旧ID竞争、缓存续接、删除旧记录、写入/线程失败清理、并发读取与原子保存、计划等待和交接。真实独立 Python 进程验证所有权阻止重复提交、正常完成报告，以及不走正常清理的进程退出；退出后需明确恢复，原限频账本仍保留两次实际尝试。

`python scripts/run_public_owner_browser.py` 用实际 Edge/Chromium 和两个本机 HTTP 服务验证：其他实例的按钮/进度、直接重复请求409且原记录不变、原工作台取消、另一实例确认续接、原缓存生成报告、关闭查看实例不影响所有者、390px和两份报告保留。上游是人工目录，外部浏览器请求为零，不是实站认证。

原每日计划实际浏览器流程也在本分支重新通过：关闭页面继续、重启补一次、固定报告保护、停止后无新请求。新脚本进入原浏览器CI，当前提交的完整/远端结果记录于PR。

## 兼容与未完成范围

新增的 `public_tasks/owner/.writer.lock` 仅是 OS 锁载体；旧岗位、报告、缓存、配额与任务 JSON 格式保持。升级或回退前先停止任务和计划，再关闭所有使用该工作区的服务并备份。旧源码不使用此所有权锁，因此不能同时混用旧/新服务并宣称互斥有效。

本功能只覆盖同一设备、同一工作区的新版本公开任务。高级采集/引导浏览器保留各自现有规则；跨工作区或设备的全局账户配额、多人权限、独立持久队列、开机自启和三站现场登录认证仍开放。
