# 列表结束时的持久化边界

Refs #215 / #210 G06 / #126。

已确定列表结束后，卡片、页签名/游标、结束原因和ready状态一次原子提交。需要翻页时，先把当前页同步保存，再调用下一页操作。保留原atomic_json、fsync、文件锁、配额、访问范围和失败处理。

## 原问题与修复范围

PR214的首次native回归在原5秒就绪等待失败，线程现场位于_gather的reading状态保存和os.fsync。底层同步写入变慢的具体原因未知；该用例8.235秒包含清理，不能当作单次fsync耗时。首次失败与唯一同配置复核均保留于 [#126现场](https://github.com/saksim/vibe_job_radar/issues/126#issuecomment-5845774488)。

代码与人工列表实测另确认了冗余提交：终态已确定时，原代码仍依次保存reading、list_end、ready。现在将相邻且没有外部操作的终态更新合并，不跨越翻页操作合并检查点。

| 人工场景 | 原任务文件同步提交 | 修复后任务文件同步提交 |
|---|---:|---:|
| 单页达到页数上限 | 3 | 1 |
| 两页达到页数上限 | 4 | 2 |
| 无下一页按钮 | 3 | 2 |
| 重复页面 | 3 | 2 |
| 无新增实体 | 4 | 2 |
| 达到100张卡片上限 | 3 | 1 |
| 重复游标 | 4 | 3 |

这些是检查点数量，不是运行耗时或实站性能承诺。每个保留的提交仍同步落盘；原5/10/600秒限制保持。旧任务身份、选择、查询范围和翻页次数保持。

## 验证

测试覆盖首次成功提交后中断、翻页之前回读、翻页异常后重启回读、fsync失败保留旧文件，以及各终态与已选卡片的保存。修复前后七个人工场景的最终卡片、页签名/游标、结束原因、范围、选择与点击次数应逐字段相同。

本项消除已证实的冗余写入；#126其他Windows等待与旧全局资格超时原因继续开放。没有新增真实登录、网站访问或历史报告重算。


## 当前主干整合（2026-10-03）

当前基线已经包含可见搜索、共同导航身份、登录返回及已关闭页面回调修复。其_gather与旧216父提交的对应方法完全相同，因而可以只移入终态检查点净修改。open_search、ensure_page_access、当前查询响应和筛选边界保持；其他方法不变，未整批引入旧父链。

六项边界测试保持原字节。新组合另做相关回归和七场景实际原子落盘对照；每个保留的提交仍调用fsync，最终卡片、选择、查询范围、游标与实际翻页次数逐字段相同。原首次失败保留，历史Windows慢因不因此认定解决。

## 中断后的显式列表续读（#52，2026-10-10）

原测试只证明重启后第一页仍在。补强为实际执行恢复后，确认旧实现重新打开首屏时会把已存签名误作新遇到的重复页，提前结束而未读取第二页。

现在对尚未结束的列表，显式“继续”通过原搜索入口和正常下一页控件重新核验有限的已存页面前缀，再进入未完成页。已存岗位、选择和签名不被重访页面替换；新的重复页、页面/100卡片上限、取消、原共享配额和网站访问判断仍然有效。重访使用正常请求并计入原账本，不退还额度，也不猜测分页地址。

页签名、原筛选或保存的页码不一致，途中缺页/空页，或旧检查点缺少可核对的位置时，明确停止并保留进度。列表可能随时间变化，不能承诺旧任务必然可续读；人工应核对原任务或另建查询。正文采集阶段仍仅处理未完成的原选择；已结束列表和自动登录返回保持原处理方式。

回归覆盖生产恢复调用、服务重建、多页前缀、原选择、变化/缺失位置、真实重复页、页数预算和取消。浏览器脚本另覆盖真实工作台的暂停、服务与采集浏览器关闭、离线重新打开、显式继续至第二页及选定正文到原报告流程。上游页面和登录状态均为人工测试数据；这些受控证据不等同于招聘网站的真实账号、滑块、短信或实站暂停恢复验收。
