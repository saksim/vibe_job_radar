# 网络兼容主需求为何仍未闭环：归因与真实交付状态

对应 Issue #23 / PR #24。本文是排查记录，不是网络兼容实现，也不能用于关闭主需求。当前已提交功能仍是公网多地址容错、显式匿名本机HTTP CONNECT和只读环境诊断。

## 1. 软件架构缺口，不是用户必须关闭VPN

TUN/VPN提供的是操作系统网络路径，Fake-IP影响的是应用获得的域名解析结果，虚拟机又拥有自己的网络命名空间。这些不是同一个开关。应按实际可用路径判断，而不是把“有VPN”本身视为失败原因。

### Fake-IP：地址检查的假设与代理映射不一致

当前代码先在本地查询目标域名，要求本次全部地址均为公网，然后向验证过的数字IP建立连接。Fake-IP返回的是代理映射地址，不是当前代码能够独立验证的最终公网目标。因此程序可能在TUN实际处理网站连接前主动拒绝。

上一轮接入的本机HTTP CONNECT仍以同一批已验证数字IP为目标，没有改变解析前提。它能解决“有可用本机HTTP代理但程序没用”的一部分情况，却逻辑上不能修复Fake-IP。仅添加代理入口或把错误提示改中文都不够。

要补齐该场景，需要明确最终目标解析、代理入口与目标地址的信任契约，并验证不会使内网目标、错误证书或重定向失去约束。当前尚未交付该契约和实现。不能将198.18.*直接称作公网，也不能将未实现归因为用户账号错误。

### 系统代理：发现配置与消费配置没有闭环

已提交的network_environment.py只读环境/系统静态代理，真实连接只消费专用VIBE_RADAR_HTTP_PROXY。用户在操作系统设置中填好HTTP代理，并不意味着当前项目就采用它。

这属于尚未完成的配置接线，不是Python或Playwright不支持代理。Python标准库支持读取常见环境/系统静态配置，Playwright也有原生代理参数；但当前项目用自建传输，需要主动集成这些能力。

### Chromium：浏览器存在不等于使用原生网络路径

当前Chromium请求由Playwright拦截，再交给Python网络桥获取并回填。HTTP和浏览器因此共同继承本地公网DNS检查和代理选择限制。只修改Chromium启动参数，不会自然修复由Python发送的请求。

需要统一请求层的策略与生命周期：前台HTTP、后台采集线程、实际连接和CLI不能分别依赖互不一致的全局环境；配置应按工作区保存，并在明确操作开始时取得快照。该界面整合仍未进入当前PR。

### 虚拟机：入口可达性不能猜测

虚拟机的127.0.0.1表示来宾自身。当前已提交代理仅接受loopback，不能直接把宿主机LAN地址当作受支持入口。宿主机代理是否监听、来宾能否到达、是否允许访问，是需要实际确认的连接条件。

支持在虚拟机中运行不等于自动拥有宿主机的代理服务。当前没有宿主机入口配置，也没有扫描或修改防火墙的能力；不能伪称已通用支持。

### 协议范围：SOCKS、认证和PAC就是未实现

匿名HTTP CONNECT不是SOCKS5；PAC需要规则求值；认证需要独立的凭据生命周期。它们不能通过改一个URL前缀实现。当前这些主体功能尚未交付，不应包装成“换节点即可”。

## 2. 本轮实际写入阻断

本轮在本地实现并验证了一套仅复用已有匿名loopback HTTP连接的工作区策略、标准静态代理选择、配置界面和路径检查；目标DNS/TLS/域名与私网限制没有放宽。

但尝试通过GitHub连接工具提交network_policy.py与loopback_proxy.py的解析接口变更时，工具仍返回：

> 因 OpenAI 无法确定请求的安全状态，已拦截此工具调用。

这两项没有写入新的Git树；本轮配套界面、工作线程整合和测试代码也没有继续作为独立残缺功能提交。它们不在PR、不在main，也不作为可运行修复附件分发。

工具未返回具体触发规则，无法准确归因为某个协议、某一行代码、用户权限或网络工具“不合法”。这是一项真实的交付阻断，但不能用它替代上述软件缺口的技术解释。

本文与Issue/PR状态更新不提供代理转发功能，也不是被拒绝代码的替代提交路径。此前已提交的窄范围本机HTTP代理和多地址修复保持原样。

## 3. 验证层也必须分开

- 已提交代码：PR现有399项本地测试，含真实本机HTTP CONNECT/TLS受控服务器；不是招聘平台或用户VPN产品认证。
- 本轮未提交实验：438项本地测试通过，包含工作区隔离、配置快照、自动选择与本机CONNECT/TLS。此数字不属于已交付PR，不能据此称main或当前分支已有这些功能。
- 本轮浏览器实验：真正Chromium在访问本机工作台时返回ERR_BLOCKED_BY_ADMINISTRATOR，尚未执行页面用户旅程，没有报告通过，也未关闭环境管理策略。
- GitHub Actions：先前任务在未取得测试执行步骤时失败。当前check-run已经出现annotation计数，但连接工具拒绝读取annotation端点；没有足够正文证据判定账单、配额或具体调度原因。不能猜测为代码失败，也不能称CI已通过。

连接代码、提交工具、CI调度、浏览器环境和用户网络是不同故障层。一个层面的失败不能证明其他层已修复或永远无法修复。

## 4. 当前可以兑现与仍需保留的目标

已提交：明确本机HTTP端口、目标为真实公网DNS时可以走已有代理；首地址不可达时有限尝试其他已验证地址；代理失效不悄悄直连，证书错误不放松校验，HTTP请求不重放。

仍未交付：Fake-IP兼容解析、真正自动消费系统代理、SOCKS/认证/PAC、宿主机LAN入口、网页网络设置，以及真实TUN/VPN/虚拟机矩阵验证。全部继续由#23跟踪，不能按“用户已要求继续”就勾选完成。

“不要因项目自身兼容缺陷阻断合法可达路径”是合理的产品目标。它不能等同于断网、失效代理、缺少权限、错误证书或网站拒绝时也必须得到正文。前者需要完成网络策略工程，后者无法由应用单方面保证。
