# 整套回归预算快照

当前资格单测上限为900秒，570秒快照仍保持；完整运行依据见 [源码资格预算](SOURCE_QUALIFICATION.md)。以下600秒时限、原失败和初始实现按其当时提交保留为历史，预算调整不定位旧根因，也不修改产品时限。

Refs #219 / #210 G06 / #126。PR209首轮Windows源码资格在600秒边界停止；最后一个START只有停止位置，没有对应的全局线程现场。[原失败记录](https://github.com/saksim/vibe_job_radar/issues/126#issuecomment-5843950747)继续保留。

原120秒诊断在每个测试开始/结束时重置，很多各自不超120秒的测试可以累积耗尽整套预算而不触发它。新增独立整套时钟，覆盖测试发现和执行，最多记录一次预算检查点。

## 使用与原时限

源码资格仍通过原subprocess.run执行，完整回归时限600秒，其他三个检查分别180秒。只给完整回归子进程增加 --suite-snapshot-after 570，同时在资格步骤元数据记录目标570秒；没有延长资格时限、原5/10秒准备等待、减少断言或跳过测试。

脚本单独使用时，需要同时声明 --progress、--report。预算必须是有限正数；未传此选项时不启动整套诊断线程。普通单测试120秒诊断及首次失败位置/后台栈保持。

    python scripts/run_tests.py --report path/to/result.json --progress --suite-snapshot-after 570

目标570秒从子进程打开进度文件、建立诊断时钟时开始计算；与父进程600秒外部时限有启动偏移。SUITE_BUDGET_SNAPSHOT记录目标、实际单调时钟经过秒数以及scope，随后保存全部线程栈。已有START/END和失败记录帮助定位当时的测试。元数据明确这是预算检查点，不能当作精确600秒强杀瞬间或历史耗时根因。

计时使用高精度单调perf_counter，并在唤醒后核对绝对目标时间。本机旧版Windows/Python的monotonic分辨率为15.625毫秒，初次短预算对照曾将50毫秒目标记录为47毫秒；原证据保留，修正后用独立目录对照，不降低时间断言。原单测试计时与超时逻辑保持。

## 清理和诊断失败

独立Event/Thread不受每个测试的faulthandler闹钟重置影响。套件早结束或发现阶段异常离开时取消等待；已经开始的记录会在关闭进度文件之前结束，避免后台写入已关闭或复用的文件描述符。诊断线程创建、启动或记录失败时只写安全的不可用标记，原测试成功/失败数量、异常和退出码保持。

记录为尽力而为：进程提前被杀、GIL长期无法调度、系统I/O完全卡住等情况不能保证留下快照；原外部时限仍可终止子进程。日志不增加参数、局部变量、异常消息或凭据；保留原进度文件10MB复制上限与上传路径，不扩大上传范围。

诊断建立时固定时钟、序列化与堆栈函数，避免套件内为测试其他路径临时替换模块属性时拦截整套观察器。独立回归先证明未隔离的实现会被这些替身拦截，再验证修正；原单测试诊断的可测试性保持。

## 实测边界

新增人工回归验证多项短测试仍触发一次整套快照、发现阶段、默认关闭、早取消、记录中清理、线程失败/诊断错误不改变结果、坏参数和原600/180时限接线。另以真实人工子进程验证终止前存在快照且没有完整通过报告，未用此短预算模拟结果冒充真实600秒Windows故障复现。

PR220初始提交5b5c6aed的Windows资格首次运行暴露两项清理测试误判：它们按线程名称检查全进程，误把外层资格运行器仍有效的诊断线程算成泄漏。原失败保存；本机启用同样外层诊断后稳定复现两项失败。修正只让测试跟踪本次创建的真实线程对象，逐个确认已终止、已从枚举移除；另加嵌套运行回归，确认内层清理后外层仍活跃、外层退出后也已清理。没有删除清理断言或修改运行器清理逻辑。

旧运行器与新运行器的本机短预算对照只回答“是否能保留整套现场”，不比较磁盘速度。当前提交的完整本机与首次CI/程序资格结果在对应PR记录；后续成功不会覆盖PR209或#126的旧失败。
