# 唯一实施蓝图｜Vibe Job Radar 0.1

## 1. 目标和非目标

目标是给定岗位集合，在允许的数据范围内发现岗位线索，提取每条 AI 辅助编程相关要求，保留原文与来源，形成可复核的能力共性/差异与可举证表达。三个不可混淆的对象：招聘要求、系统归纳、候选人实际证据。

非目标：全国招聘平台全量保证；绕过登录、验证码或账号权限；批量收集招聘者联系方式；自动投递；假造简历事实；把学历/年限包装成已满足；用生成字数或代码行数证明业务价值。

## 2. 数据流

```text
平台域名 × 岗位别名 × 编码概念/工具关键词
  → 搜索任务清单 + 预算 + 执行台账
  → snippet 线索仓库
  → 获准公开正文 / 用户授权文本与选区
  → 独立正文识别 + 数据来源声明
  → SQLite 版本快照 + 观测记录
  → 新鲜度/过期/岗位/平台/合成数据过滤
  → 跨来源保守去重
  → 精确原文切分与能力要求提取
  → 规则接收 / 人工待审 / 可选模型提案
  → 样本内能力并集、交集、频次和岗位差异
  → 候选人证据逐条映射
  → 通用模板 + 岗位模板 + 证据指标 + 缺口
  → CSV/JSON/MD/HTML + 文件哈希清单
```

## 3. 平台接入策略

分“发现”与“获取正文”。发现统一用配置中的域名调用搜索服务，不杜撰平台官方接口。正文通过本地材料、用户浏览器选区或获准 HTTPS 页面输入。公开页面优先识别 Schema.org JobPosting；独立 DOM 容器为次级、待实站验收的兼容路径。

泛化接口不是保证所有平台都可自动抓取。新平台加入域名配置只获得搜索路由；页面解析、访问授权、正文完整性与线上验收必须逐项完成。动态 JS 登录页在 V0.1 不用浏览器自动化渲染，更不抓移动端私有接口。

## 4. 模型与版本

JobRecord 对 title/text、来源模式、合成标识、证据等级、带时区采集时间作严格校验。source_mode=search_api 只能是 snippet。synthetic 与 source_mode 必须一致，禁止字符串 false 被误判成真值。

record_id 是来源身份、证据等级、合成命名空间与正文的内容哈希。重复导入不生成新快照，但追加来源观察。改动正文生成新快照。选“当前版本”按采集时间排序，不允许晚导入的旧记录覆盖新采集记录。

跨平台去重要求已知公司、标题、地点和正文归一化后一致；未知公司按来源隔离。不同公司使用相似模板不自动归并，模糊聚类暂不做。相同模板是否真的对应同一个空缺仍需抽检。所有来源保留；原文偏移只针对代表正文，不宣称同一偏移可套到其他来源。

## 5. 抽取和语义边界

direct：原句出现 Vibe/AI 辅助编程、特定编码工具或大模型编写代码的直接锚点。

contextual：同一行附近或明确 AI 编程小节具有锚点。默认待人工复核。

role_related：同一个 JD 的其他工程/领域能力；单独输出，但不计入 AI 编程要求频次。不把“算法/Agent/MCP”任意命中直接当作 Vibe Coding。

强度包括 required、expected、preferred、not_required、prohibited、unspecified。在可识别的混合句中按逗号后的新义务/否定拆分，不随意拆开工具列表；复杂否定仍进入待审。同句多项能力按能力标签分多行，quote/start/end 不变，因此行数不能直接当独立原句数。

rule_score 仅为可解释的规则优先分，不是模型置信概率。规则抽取不是经招聘市场金标准验证的精确语义解析。V0.1 的首要质量措施是来源、切分、范围、否定和人工复核，而非假装规则召回率为100%。

模型增强使用明确授权、结构化 schema 与本地验证。JD 是不可信数据，不能执行指令。严格检查 quote == text[start:end]；错误偏移拒绝，不采用模糊回填。缺点是模型可能返回正确语义但错误中文索引，从而被拒绝；这是保守选择，拒绝率见 llm_audit。

## 6. 汇总公式

在给定岗位范围内，J 为至少包含一条已接收正向 AI 编程正文要求的去重职位集合；J(c) 是包含能力 c 的职位集合。

sample_frequency(c) = |J(c)| / |J|。

这是经过条件筛选的样本内部频次，不是全体职位中某技能的招聘比例；不是随机抽样置信估计。每项能力在同一职位重复出现只计一次，多个平台重复岗位去重后计数。

intersection：该样本集合全部职位都出现。common：频次达到配置阈值（默认0.6）。specialized：其余出现过的能力。阈值是本项目的归纳规则，并非行业标准。样本过少时不构成“市场共识”。

分岗位分别计算分母，避免架构职位大量出现使时间序列岗位的需求被掩盖。原文所有限定仍由逐条矩阵承载，归纳层不删除要求。

## 7. “万能描述”的可实现定义

不采用“一个自然段完全满足所有招聘方”的定义，因为学历、年限、所在地、工具经验、数据权限和岗位方向不能靠措辞改变。

可实现交付为：共同能力底座 + 每种岗位的专属补充 + 真实观测指标 + 原文逐条映射 + 尚未覆盖的条件清单。候选人只声明能力类别时，状态是 capability_only_not_satisfied；必须明确 requirement_ids 和人工确认，才形成 user_attested_exact。

映射覆盖率 = Σ已人工逐条映射的正向要求权重 / Σ已接收正向AI编程要求权重。默认 required=3、expected=2、preferred=1、unspecified=1；权重为可配置设计，不是招聘方真实评分。硬资格和限制条款不纳入该比例，必须另看。即使显示100%，也只是该口径下的映射完备，不是完全满足岗位。

对显式生产/上线要求，离线证据不得直接计入。生产指标仍是输入方声明与人工确认，不是软件替用户做了生产审计。

## 8. 可观测与故障处理

搜索有请求上限、分页状态、排除原因和服务级停止。抓取有明确许可、robots、公开IP解析与固定连接、域名证书验证、字节/超时限制、重定向拒绝、401/403/429停止及挑战页拒绝。

导入逐行隔离错误，完整错误报告不因存在成功行而省略。分析输入逐条记录剔除原因。LLM失败产生 incomplete 状态及退出码2。输出在同目录临时目录内生成，成功后原子替换到新报告目录；不覆盖已有运行。

SQLite 是本地单写者工作负载设计，适用于研究型中小样本集合。分析阶段会把当前记录加载进内存，尚未对十万级/百万级 JD 做容量测试，不把它叫分布式生产平台。

## 9. 后续最小施工顺序

先获得授权的真实 JD 标注集，并测量逐条抽取精确率/召回率、否定准确性、岗位分类与去重误合率。没有这一步，不扩展“高级文案”功能。

然后逐平台验证访问与解析，只对获得允许且稳定的路径新增适配器。再补检索跨运行缓存、复采调度、JD变更差分和模型总预算。最后考虑审阅UI、可插拔LLM、运行时XLSX和更精细的需求组合约束；均不得削弱原文证据门控。
