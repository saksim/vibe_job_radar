# 回归测试失败瞬间证据

scripts/run_tests.py 默认在断言失败、未预期异常和失败子用例发生时采集有界线程调用位置，早于 tearDown 和 addCleanup。使用 --report 时同步追加并刷新同目录的 .failures.jsonl，原 .log 也保留同一事件；成功、跳过和预期失败不采集。

额外证据只记录父用例标识、耗时、最多16个线程各24个函数位置（文件名、行号、函数名）及截断数。不记录线程名、完整路径、源码、局部变量、异常正文或子用例参数。原 unittest 失败正文保持原样，其隐私范围与新增证据不同。采集或附加文件写入失败不覆盖原失败或阻止清理；原日志给出固定诊断不可用标记。

不需要修改工作流或开启 --progress；该选项原有逐项记录及120秒看门狗保持。生产代码、15秒等待、断言、磁盘同步和CI预算保持。

## Python 3.10 的失败报告时机

PR258首轮Python3.10的新诊断有3项失败：该版本在清理后才调用结果回调，仅重载 addFailure/addError 会错过线程。原head 6fc2d927、run37159184114/job111308836235/attempt1 和完整日志保留；这是新诊断兼容性缺陷，不是PR257等待原因。

修正沿用 unittest 的异常处理边界，在异常交回原处理器之前记录，再原样传播；不改写失败/错误/跳过/预期失败/中断行为。标准结果回调保留作为其他错误的回退，同一异常只记录一次；每项结束后恢复原边界并释放异常引用，嵌套运行也还原。直接以Python3.10和3.12验证清理顺序与结果，而非只模拟版本号。

参考CPython官方3.10实现：https://raw.githubusercontent.com/python/cpython/v3.10.21/Lib/unittest/case.py

## 保留标准断言的源位置

交叉核验旧193诊断时发现第二提交的生成器观察器会在Python3.12断言栈前增加普通脚本帧，标准unittest清理框架帧时可能提前截断到观察器，丢失原断言源位置。当前使用上下文对象直接委托原 __enter__/__exit__，把原异常类型、对象和traceback直接交给原处理器，不增加生成器yield帧。新增行为对照同时验证普通断言、异常和失败子用例与标准unittest保留相同源行。旧组合首次59项中1失败及当前负对照保留；不靠后续CI通过覆盖原缺陷。
