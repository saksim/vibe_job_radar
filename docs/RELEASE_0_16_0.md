# 0.16.0：配额等待、页面退休与PAC撤销修复

基于正式0.15.9，保留现有功能，按dev→release→main晋升；正式交付以Tag和附件为准。

## 解决了什么

- #497：配额预留取得SQLite写锁后再读取一次当前时间，避免等锁后的旧时刻导致误报时钟回退、冷却误拒绝、页面间隔缩短或漏检真正回拨。
- #496：同步CDP回复须仍属于有效pending、存活会话与同一client才交给业务回调；已关闭页的旧JSON不再污染当前采集结果，也不会因旧无效响应误停幸存任务。
- #498：TCP/代理隧道及TLS阻塞返回后重新检查PAC许可，已有连接发送前同样复核；撤销后停止目标HTTP并关闭自有连接，清理错误不覆盖pac_revoked分类。

## 提高了什么

保证排队后的配额判断依据实际取得写锁的时间，保留完整的下一次访问间隔和真实时钟回退保护；把页面生命周期与业务结果绑定；缩小用户撤销PAC许可后仍发送请求的窗口。既有搜索、完整JD、原报告、代理认证、DNS/TLS、配额、团队服务、调度、备份与自动升级保留。没有延长SQLite等待或验收期限，没有去除fsync、降低持久化、放松断言、增加重试或回退直连；不声称已量化整体速度提升。

## 验证结果

- 配额：准确0.15.9旧源码四个真实SQLite并发负对照全部失败（0.172秒）；修后四项通过（0.407秒），一次70项相关回归全通过（13.875秒，无跳过）。用真实两个连接和线程事件控制写锁，不以sleep制造概率。
- 原生页面：准确旧源码新增三项为两失败、一正常控制通过（0.179秒）；修后一次86项相关回归全通过（3.594秒），覆盖真实业务回调、活动页和异步晚回执。使用人工CDP输入，未启动真实招聘浏览器。
- PAC撤销：准确旧源码四项为三失败、一正常控制通过（8.453秒）；新增清理错误子场景的首失败同样保留，修后最终五项通过（8.545秒），一次48项相关回归全通过（19.523秒），包含自有本地HTTP/SOCKS夹具。没有外网请求、公开程序下载或执行。
- 测试发现共3579项，比0.15.9新增12项；发现操作不等同完整执行，本地未重复全矩阵。代码同行复核不冒称真人验收。

候选与准确main仍须各自必要CI和实际程序产物证明；按dev→release→main晋升后发布三个正式Tag并核验公开摘要和旧版升级解析器。实际完成状态记录在总控#57。
