# 原生控制层：减少页面运行时事件采集

关联 #63 / #49 / #50，基于已验 PR195 的源码候选。此变更仍需独立检查和实站验收，不能算作正常关键词搜索或账号登录已经打通。

## 已观察到的问题

2026-09-25 的本机离线对照使用 Edge 153.0.4234.48 和此前保存、字节未改动的公开脚本。普通 Edge、仅启用标准自动化标识的 Edge、仅启用 CDP Page 导航的 Edge 均保持页面正常；相同启动条件增加 `Runtime.enable` 后约3.68秒转为 `about:blank`。普通 Playwright 和微软官方 WebDriver 也复现清空。完整条件、阴性结果和结论边界见 [Issue63 的实验记录](https://github.com/saksim/vibe_job_radar/issues/63#issuecomment-5829546119)。这些实验没有请求招聘站、使用账号、解锁或修改原脚本，也不能证明全部历史实站失败同因。

本机 Playwright 页面初始化会无条件订阅 Runtime 事件。应用删除 console 回调并不能取消底层订阅。新的 native 控制层只执行工作流需要的 DOM 读取、标准 Input 输入和页面导航，不订阅整页控制台对象。`navigator.webdriver` 保留，站点脚本和 console 方法保持，现有 VibeJobRadar 网络标识继续由原请求控制器设置。

## 实现边界

- 默认 HTTP bridge 仍使用原 Playwright 后端。显式 native 选择使用本候选的控制器；失败不自动切换路线。
- 只启动应用专属进程、全新临时 profile 和隔离 context。控制通道使用父子进程继承的匿名管道，不开放调试TCP端口；不连接日常 Edge、读取其 profile 或导出账号。协议内容不写日志。
- 复用当前Playwright发行包已有的Node可执行文件；小型桥接脚本只转换管道消息分隔符，不修改SDK或过滤站点脚本，没有新增安装依赖。单消息8MB、接收队列16帧、同步待答命令32个，操作只在所有者线程执行。站点网络继续经过原 NativeTunnel 和已选择的网络策略。
- 原 Fetch 请求/响应检查、robots、共享配额、逐跳校验、业务关联、401/403/429、取消、TLS验证和会话同意逻辑继续使用 NativeBackend。DOM/Input 层不发送或拼造站点业务API。
- 每份原生文档在保留发布方所有 CSP 的同时追加限制：同页表单与脚本可执行；弹窗、frame、worker和WebSocket保持不支持。文档解码正文保持，限制在执行脚本之前交付；robots仍是不可执行的控制数据。HTTP/HTTPS的 `connect-src` 不匹配 WS/WSS，依据 [CSP scheme 匹配](https://www.w3.org/TR/CSP3/#match-schemes)。
- 正常表单点击与输入采用浏览器 Input 事件。字段内容不进入诊断；Cookie仍由浏览器保存。导出保持原 SameSite默认和分区Cookie排除规则，不扩大持久保存范围。
- 实际主页面清空仍是失败，旧结果仍会清除。没有吞掉错误、重试被拒绝的登录、修改保护逻辑或改变完整JD标准。

此处的小型 DOM 接口只覆盖已审查适配器的 selector、可见性、输入、点击和分页需求，不承诺替代整个 Playwright API。新控制器也没有扩大站点契约、开放BOSS/51job原生采集或解决默认带参数搜索入口的访问规则问题。

## 验证

本机已完成无网站导航的真实 Edge 启动检查：原控制器成功绑定主页面/临时页面、DOM读取、标准文本输入/按钮点击、自动化标识及专属profile清理通过。独立的离线原型还验证了表单→HttpOnly会话→搜索→自建正文、拒绝未知写请求及403停止；这不是本候选完整TLS/CORS资格。

把原公开脚本放入实际新后端的自建页面后，首个完整观察因脚本上报请求不属于测试域名而以`resource_domain_blocked`停止。该失败保留；随后独立的只读观察保持后端原错误与halted状态，记录可见页面约10.06秒未清空、输入和Cookie形状可读、实际发送0请求。它只补充页面行为证据，不能算作可用的采集流程；没有删除该请求校验或把错误改为成功。

单测覆盖控制事件归属、嵌套命令、不必要订阅拒绝、协议内容脱敏、线程所有权、消息限制、管道分帧/断开、页面退休及Cookie兼容。原 Linux/Windows、headless/headed 的真实浏览器人工TLS、CORS、认证代理、分页、保存和报告检查继续执行，不能用单测或该离线原型替代。当前提交的实际成绩以对应PR为准，不预写未来通过数。

PR196 的早期CI暴露了启动和输入兼容性问题，原工件与每次提交的结果均保留在PR记录中。控制器恢复旧启动器对Linux、固定试验配置和后台组件扩展的参数；本机配套Chromium的空白未知目标后来变为内部工具栏，恢复配置后即可启动，无需放宽未知目标规则。点击先等待绘制并核对命中位置，随后等待其引起的新文档，不把输入确认当成导航完成、不重复表单提交。延迟400ms的自建表单已验证点击在新DOMContentLoaded后返回，带原限制CSP仍可正常提交；最终TLS/CORS资格仍以同提交CI为准。

原浏览器验收还增加了实际报告链接就绪与非空编号检查，再执行原报告保留断言。同一次首轮CI中的旧报告写盘5秒等待失败保持在Issue126；不通过扩大时限或移除fsync处理，之后新提交通过也不能证明历史原因已全部解决。

## 连续暂停事件与命令回调

`e9be480` 自身21/21首次CI、2180项完整回归、四种原生14步主流程/19步表单和实际exe既有流程均通过。随后唯一实站观察仍在入口触发`native_observation_limit`，第一错误发生在输入前，未观察到主页面跳白；没有重放，正常搜索和账号均未验通。原记录保留第一错误及停止前后计数，但没有限额所在行，因此不能断定唯一原因。

新的离线场景确认了一个控制缺陷：导航过程中连续80个Fetch暂停事件，每个回调同步发送拒绝命令；旧pump在等待应答时又立即调用下一事件回调，形成递归，达到原32条待答命令上限。这个失败在修改前已实际重现，不能用提高该上限处理。

现在回调等待命令应答期间，后续已订阅事件进入FIFO队列，当前回调完成后再处理；外层命令返回前会排空已收到的事件，确保导航和会话退休对调用者可见。原命令32条、单消息8MB、接收队列16帧、线程归属及超时保持；新增延后事件同时受512条和总8MB约束，未订阅事件不占该队列，关闭后清空。请求仍逐条走原检查，不继续已拒绝的请求或发送额外业务请求。

测试覆盖80事件顺序、回调深度1、命令并发不超过2、导航在外层返回前可见、退休会话丢弃后续事件、队列条数/字节限制、原截止时间、异常恢复与关闭清理。人工HTTPS表单页再同时产生80个独立可选请求，等待全部原生拒绝后才显示输入框，验证实际浏览器在原规则下继续搜索、完整JD和报告。后续完整回归、四模式CI及新的实站结果另记，不把离线复现直接当成实站根因确认。

本机真实 Edge 153.0.4234.48 的独立空白页对照也复现该缺陷：80次自建片段变化，每个事件读取帧树，旧版回调深度及待答命令均达到32，首个回调错误为`native_observation_limit`，没有回调完成。候选版按顺序完成80次，深度1、待答最多2；两者外部隧道连接均为0，专属profile均已清理。第一版测试误将刻意片段变化触发的`PageSnapshotChanged`当作意外失败，该原始结果保留；修正测试预期后候选通过，生产快照保护没有修改。这只验证真实浏览器控制层，不替代人工HTTPS场景或招聘站实测。

## 就绪等待中的页面变化

`d26d51d` 的首次 Windows headless 人工搜索验收已完成16项表单检查，随后打开窗口隔离场景时，页面更新查询参数与 `body.count()` 同时发生。CDP正确地以 `PageSnapshotChanged` 丢弃旧读取，但 `_settle` 将这次正常页面变化直接传到任务。修改前的单测已复现同一异常出口。

等待阶段现在只捕获这个明确的快照变化信号，在原15秒总时限内重新读取当前页面；不重置时钟、重导航或重复输入。重复变化仍超时，取消、原生拒绝、验证提示和其他读取错误仍停止。新增测试覆盖计数、文本和整页快照变化，以及截止时收到拒绝的原原因保留；底层快照有效性检查保持。

同提交的 Linux headed 是另一处失败：自动非空收集期间，当前搜索请求在HTTP200后报告 `net::ERR_FAILED`，不是已记录的取消或旧请求。该日志没有保留具体CORS/拦截类别，不能据此认定根因。人工验收观察器补记 `Network.loadingFailed` 的固定 `blockedReason` 和 `corsErrorStatus.corsError` 枚举；未定义值标记为未分类，不记录 `failedParameter`、URL、请求内容或原始错误文本。依据 [CDP Network 定义](https://github.com/ChromeDevTools/devtools-protocol/blob/master/pdl/domains/Network.pdl)。生产请求及失败处理不因观察器而改变。

后续无外网 Linux 容器保持 d26d51d 产品源码不变，使用与CI相同的 Playwright 1.63 / Chromium 153；观察到间歇性的 `MissingAllowOriginHeader`，响应暂停时HTTP200且头部数量为0。人工源的本地 NetLog 对照进一步记录：同一搜索接口前一响应是含完整CORS头的HTTP/1.1，失败响应却被解析为无头的HTTP/0.9；服务器实际发出的所有POST响应均带CORS。原日志和中间一次完整通过均保留。

人工HTTPS服务器把空字符串压缩成20字节，错误地随OPTIONS 204发送。浏览器按204无正文语义复用连接，遗留字节破坏后一个响应；两个真实回环TCP测试在修正前均失败，直接验证了这个传输错误。服务器现在不给204/205压缩或写正文，204也不发送Content-Length，遵循 [RFC9110 8.6](https://www.rfc-editor.org/rfc/rfc9110.html#section-8.6) 和 [15.3.5](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.3.5)。其他成功/拒绝响应、原21项搜索断言及生产CORS处理保持。此因果链已由本地原始数据复现；旧CI没有NetLog，不能把它扩大为所有历史网络或真实网站失败的唯一原因。
