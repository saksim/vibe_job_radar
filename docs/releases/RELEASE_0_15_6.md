# 0.15.6：附件上传恢复与手动保存事务

## 解决了什么

- #467：个人附件直接写最终路径，磁盘写入中断会留下阻碍重传的残文件；容量查询未与登记串行，竞争上传能越过100个上限。现在先在私有暂存目录写完、flush/fsync后发布，容量检查与登记使用同一SQLite写事务。元数据失败保留完整文件供重试核验登记，文件/数据库失败返回可操作提示，原附件损坏仍明确拒绝。
- #468：手动保存JD原先分开提交快照/观察与审计，后一步失败仍留下新岗位或重复观察。现在复用已有批次事务，共同提交或回滚，重试保持原去重与观察计数。

## 提高了什么

失败后可重新上传附件或保存JD，避免用户看到失败却留下半次操作；保持50MB/100个附件上限、单附件1MB上限、哈希核验和个人材料本地保存。已有批量导入、来源校验、角色识别、完整原文、复核/撤回、个人报告和旧版本历史保留。网络、协作、升级和回滚功能不变。

## 验证结果

准确0.15.5基线7项负对照出现7个断言/子用例失败、1个错误（0.393秒），原附件防篡改正向对照通过。修复后7项定向回归全部通过（0.386秒）；个人证据、原报告、工作台和导入共100项相关检查99通过，1个已有符号链接权限跳过（18.837秒）。未重复本机全套。

使用临时自造附件/JD、磁盘写入/flush错误与SQLite触发器；竞争用两个真实SQLite连接确定性交错，无等待碰概率。它们不代表真人材料、实站或普通净机验收。候选与准确main仍须各自必要CI；按dev→release→main晋升后发布Windows、Python及Linux/macOS正式Tag并核验附件。这里记录的是发布计划，实际结果写入总控#57。
