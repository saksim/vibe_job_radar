# 工作区升级与回退验证

本次验证范围是主干 `ec458799`（PR61）与能力状态增量，不声称任意旧版本、所有插件或未来 schema 都兼容。使用临时人工工作区，三个独立 Python 进程依次运行旧源码、新源码、旧源码；没有招聘账号、用户文件或来源网络请求。

旧源码建立 schema 1 的岗位数据库、完整人工正文与旧报告、本人证据的人工草稿、原生模式中断检查点、一次持久配额和人工 Cookie 快照。新源码读取这些数据，不启动浏览器、不续跑检查点，生成带附加软件能力快照的新报告。再用原旧源码读取旧/新报告、岗位和个人证据，并恢复人工 Cookie。

检查原始岗位/个人证据/配额行、历史文件哈希、任务 ID 与后端、schema 版本、会话内容和报告可读性。该流程验证的是持久格式和升级/回退，不是实际原生浏览器或真实登录认证；后者仍由各自浏览器/实站验收负责。Windows 与 Linux CI 单独执行并保存结果，不把本地测试代替远端通过。

维护者可在独立 checkout 上重现：

```text
python scripts/check_workspace_compatibility.py --old-source <已检出的ec458799源码目录>
```

结果写入 `browser-acceptance/compatibility/results.json`，人工临时工作区完成后清理。脚本不接受用户现有工作区作为整体验收输入；内部 `--phase` 参数只用于同一脚本的测试子进程。

用户更新时先退出旧工作台终端，备份完整工作区（包含原文、报告、个人证据、配额和自行选择保存的会话），用原有可用解释器启动完整新源码。无需删库或重装环境。回退使用已核验的旧源码；如果跨越其他数据库或来源格式变更，则使用对应完整备份。仅刷新旧网页不能切换正在运行的服务代码。

本次只给新报告添加 `software_acquisition_capabilities`，不改历史报告，不改 jobs.sqlite schema 1、Cookie 文件或检查点 schema，不升格岗位真实性。比 `ec458799` 更旧的版本可能不认识 `browser_fetch` 或其他来源字段，本验证不能代替它们的单独回退验收。
