# 公开目录版本校验

Refs #101 / #9 R5 / #30 H3-H4。仅适用于已登记的Anthropic、Cloudflare固定公开GET目录。它减少目录未变化时的正文传输，仍不是逐条源端增量、跨设备水位或全天服务保证。

首次明确获取仍下载并验证完整目录。后续超过10分钟本机缓存窗口时，如来源提供有效ETag且同一完整缓存仍可信，就携带该版本标识请求同一固定接口。

304确认同一版本时，原正文、采集时间、快照和分页游标保留，另记录服务器确认时间。页面说明“确认目录未变化”；报告的`public_source.json`保留`collected_at`、`source_checked_at`、`not_modified`及本次请求数。原变化审计保存在原缓存/旧报告，新304报告不重复把旧变化当成新发现，也不制造岗位关闭结论。

新的200正文重新完整验证、保存采集时间，并与上一份完整目录进行原增改/未出现审计。后续刷新失败仍显示过期缓存，两个已有时间都不向前伪造。每日计划复用相同逻辑，经过新200或合格304确认的结果才不算过期。

## 请求与失败边界

- 只接受单个、有长度上限、无控制字符的ASCII实体标签，不接受星号、列表或注入额外头。只发匿名GET和固定Accept/identity编码，不携带查询词、账号、Cookie或个人材料。
- 只有显式条件GET才能接受304，必须有完整有效正文和匹配版本标识。缺失/矛盾ETag、重定向或无正文缓存均停止，不自动补第二次请求。普通API及旧单岗位案例保持原严格行为。
- 每个304计入原30秒、12/小时、24/滚动日额度；两来源及单岗位案例继续共享。429冷却保持，403等硬错误后不发送旧条件，必须重新取得合格完整200才能恢复。
- 新鲜度可由确认时间延长，但完整正文仍有原7天上限，届时要求完整200，不无限依靠304保留旧正文。

语义依据为[RFC 9110：If-None-Match](https://www.rfc-editor.org/rfc/rfc9110.html#name-if-none-match)和[304](https://www.rfc-editor.org/rfc/rfc9110.html#name-304-not-modified)。真实服务器是否返回304须分别观察，人工响应不作为真实源支持证明。

## 兼容与验证

原`*-board-v2.json`格式保持。元数据独立写入`*-validation-v1.json`，绑定固定API、缓存修订、采集时间与请求格式。损坏、错来源、未来时间或符号链接拒绝；快照/格式不一致不使用旧条件。200先原子写正文、再写元数据，中断后的旧元数据不能为新快照提供新鲜度。

回退前停止工作台并备份。旧源码继续读取v2正文、忽略新增元数据，可能重新完整请求，但不会把确认时间写成新采集时间。原凭据、配额、所有权、硬错误与报告保持。

验证覆盖条件GET边界、304/200、硬错误/429、重启、来源隔离、游标、两个时间、原报告/计划及实际Edge界面。当前head结果、首轮失败和真实源状态/计数记录在PR；不上传整份JD或升格三站认证。
