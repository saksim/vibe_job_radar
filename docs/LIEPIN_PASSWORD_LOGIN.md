## 可用行为

向导第 3 步增加“猎聘：自动填写密码并提交一次”。用户在本机输入自己的账号密码并授权本次提交后：

1. 保留原查询或下一条未完成的所选岗位，在程序拥有的猎聘页面打开登录。
2. 点击页面的“密码登录”并填写当前可见表单。程序只读取猎聘条款框：已勾选时点击一次登录；未勾选时返回 `login_agreement_required`，明确提示用户在猎聘网页勾选条款后再点击该页“登录”。勾选本身不提交，程序不代为同意或自动重试。无法唯一识别条款框时停止填写。使用网站自身 JavaScript，不构造或重放密码 API 请求。
3. 密码仅通过受本机令牌和 Origin 校验保护的现有工作台 API 进入工作线程；不写任务、报告、诊断或 Cookie 快照。界面立即清空，线程结束和浏览器填表结束均释放引用；Python 字符串不能保证内存擦除。
4. 正常返回本任务可读列表/完整所选详情后，沿用既有两次稳定观察与采集接续。启用“搜索后自动采集前 N 个”可继续已有选岗、入库和报告流程。
5. 平台协议、验证码、短信验证、密码错误由平台页面提示处理。程序不勾选协议、不处理验证码、不重试密码。已恢复的 Cookie 会话仍由正常页面实际结果判断可用性。

手动登录勾选自动接续时保留原查询意图。原生模式的无关键词入口在账号区域与搜索框连续可见、登录/验证控件消失后，重新核对原任务并提交原关键词一次；带显式筛选、已有结果或所选详情不改作新搜索。具体条件见[登录入口接续](LOGIN_SEARCH_ENTRY.md)。这仍需本人账号与实站验收。
旧手动登录 API 继续拒绝密码，单独的 `login_password` 动作只支持猎聘，并要求一次授权。

用户已确认：猎聘网页条款框出现勾选状态，但登录没有继续；日常 Chrome 可以完成真实登录。该次观察的采集窗口是独立 Edge；仅在 Chrome 打开工作台不会切换采集引擎。随后 #205 已增加并实测明确的 Chrome 原生采集选项。此对照尚不能证明 Edge 引擎故障。

原真实任务另有 `native_operation_unreviewed` 停止。保留日志在登录动作结束后，仍有成功资源响应，随后账号服务的 OPTIONS/XHR 被阻止；具体路径已被旧脱敏格式遮去，不能推定哪个接口或直接放开。新增 `first_backend_stop` 在控制器第一次停止时保存当前脱敏观察，避免可选资源失败及后续连带拦截覆盖它。单独保留 Preflight 类型；仅对已记录公开脚本里的9个精确账号接口保留固定路径，未知路径、查询值和所有正文仍不保留。该名单只用于诊断，不授予请求许可。

真实账号登录、滑块/短信、所选完整 JD 和原报告接续仍待验通。旧服务的已有日志不能靠更新代码补回丢失信息。

## 默认短信页没有切换到密码页（2026-09-26）

用户在 Chrome 原生工作台再次操作后，原任务返回 `login_form_changed`，账号密码均未填入；用户确认页面仍是默认的“手机号＋短信验证码”。该次脱敏诊断中 `first_backend_stop` 为空，后续资源仍有正常响应，不能把它归为密码错误、未勾选条款或已证实的网络停止。

旧入口逻辑只检查密码输入框是否可见；不可见时会先点击页头 `#header-quick-menu-login`，然后才点击“密码登录”。已打开的短信弹窗可能遮住页头。独立 Chrome156.0.8072.0 的本地对照复现：页头点击等待失败，密码标签点击0次，文本字段全空，返回 `login_form_changed`。这是与反馈一致的可复现代码缺陷；未取得当次真实页面结构，不能将模拟对照当作实站根因证明。

修复先查找唯一可见的“密码登录”标签；已有登录框时直接切换，只有标签不存在时才打开页头入口。两种浏览器后端统一忽略隐藏的同名标签，遇到多个可见标签停止。确认密码表单出现之后才填写，条款继续由用户本人处理。入口打不开、标签未切换、密码表单未出现分别记录 `login_entry_unavailable`、`login_password_tab_unavailable`、`login_password_form_unavailable`，不读取或记录账号值。

原10项浏览器场景保留，新增7项：已打开的短信弹窗、内嵌短信框、尚未打开的入口、隐藏同名标签、延迟出现的标签、可见标签歧义、点击后仍是短信页。检查短信字段不被填写，最多切换一次，不点击真实条款或提交按钮，凭据引用始终清理。新增场景随原 `verify_password_form.py` 在默认浏览器桥与原生 CDP 检查中运行。

初始离线复现的断言把 checkbox 默认值 `on` 误算成“字段已填写”，导致辅助脚本断言失败；保留原输出，改为仅检查文本/密码字段后完成旧版对照。实站页面、账号、Cookie和网络权限均未因此改变。修复后的真实账号登录、滑块/短信、所选完整JD和原报告仍须另行验证。

第3步现在在填写前读取共享账本的可用状态，显示实际限制原因、按本机时区计算的下次允许时间，以及当前是否确实存在采集窗口。受限时清空并禁用本地账号表单和两个登录按钮；状态轮询确认到期后才恢复操作，不自动提交。账本读取失败时显示暂不可用，不推测恢复时间。

可用状态只读，不持久化到任务、不消耗或退还次数；实际动作仍经原子的 `reserve()` 检查。最小间隔、滚动24小时上限、共享等待期和时钟回拨处理使用同一计算，原数值及网络范围保持。刷新页面、创建新任务或重启不会重置配额。

6项单元检查覆盖无副作用读取、重启后滚动窗口、精确到期边界、较长共享等待期、时钟回拨及读取后被其他动作占用。`python scripts/run_login_quota_browser.py` 使用临时合成账本和时钟，实际浏览器验证填写前提示与禁用、到期后无自动请求、共享等待期及390px布局；不访问招聘网站。该测试加入原浏览器CI流程，旧场景保持。

## 验证方法

- `python -m unittest discover -s tests`：包含隐藏模板与可见验证页、已下线职位、密码单次授权/字段校验、任务与状态不含密码、异常清理、原查询接续和精确请求规则。

- `python scripts/verify_password_form.py --channel msedge --native`：同样17场景通过生产 CDP 页面/输入实现；CI 也运行配套 Chromium 的此模式。
- 所有新登录验证均是受控验证；实站读取的原始 HTML 与临时公开脚本留在忽略目录 `.verify`，不提交原始页面、账号或第三方脚本。
