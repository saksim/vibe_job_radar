# 浏览器采集：同工作区只由一个服务控制会话

关联 #93 / #49 / #50 / #52 / #9 R4 / #57。基于 #90 的公开任务所有权修复，独立补齐向导浏览器、正常登录接续和原 HTTP 失败转交入口。

## 修复的问题

旧行为已用两个真实向导服务和人工浏览器复现：原服务仍在读取，第二处却把状态显示为“上次服务已退出”；第二处停止操作将检查点写成 stopped，并声称浏览器关闭，原浏览器却继续运行，随后重新覆盖为 ready。原有进程内锁及可选 Cookie 保存锁不能保证整个浏览器会话只有一个所有者。

本分支先取得工作区 `guided/owner/.writer.lock` 的 OS 锁，再读取决策、保存任务和排队；持有到动作结束且采集浏览器关闭。该锁由操作系统释放，不用 PID、修改时间或残留文件猜测进程是否存在。检查点另用短暂的跨进程读写锁，覆盖 Windows 的文件句柄和元数据探测。

## 用户可见行为

- 另一个工作台能看到当前已存进度和结果，但不会擅自把仍有所有者的任务显示为中断。页面说明应返回原工作台，禁用采集动作和密码输入；直接请求提交、停止、继续、登录、组件操作或诊断变更同样被拒绝，返回 409 / `guided_task_busy`。
- 暂停保留浏览器、等待正常登录、限频等待、完成一批但仍保留会话时，所有权继续保留；关闭工作台网页也不交出会话。按原“停止并关闭登录会话”完成关闭，或者原服务真正结束后，另一处才可明确继续原查询。没有自动重开窗口、切换身份或重放密码。
- 关闭仅查看进度的服务不取消原工作台的动作。原服务退出超过等待时间但后台动作仍活着时，锁继续保留；不会把超时当作进程退出。
- 若浏览器关闭操作本身抛错，当前服务显示无法确认关闭，保留所有权并拒绝新动作。需要退出原工作台进程、核对浏览器后重开；不声称关闭成功，也不让另一服务抢走可能仍在运行的登录会话。
- HTTP 失败转交同样在整个新检查点到排队期间保持锁。原失败任务、已存正文和 HTTP 预算不改变，不能从另一入口绕过所有权。

本次不变更检查点 JSON、Cookie 数据格式、原报告或配额计数；文件格式兼容不等于旧版本也懂新锁。升级/回退先停止任务、关闭全部同工作区服务并备份，不能同时运行不具备此修复的旧版本并声称互斥。公开任务与浏览器任务仍使用各自的来源与预算，不合并身份。

## 验证和边界

新增双服务/独立进程回归覆盖状态、误停拒绝、密码早拒绝、组件/诊断操作、暂停/关闭、线程启动失败、退出超时、关闭不确定、原报告/配额和 Windows 并发轮询。独立进程退出测试确认 OS 自动释放，而不是手工删除锁文件。转交入口另有两个竞争边界回归。

实际 Edge 和两个 HTTP 工作台验证：390px 控件与提示、直接 API 409 且检查点不变、明确关闭后接续原查询生成原报告，以及关闭观察服务不影响新所有者。来源均为人工夹具，零招聘请求；已有正常登录返回、Cookie、原会话复用、限频与有限重试仍分别回归。

最初回归发现同步构建的嵌入式会话没有 worker 时，旧 close 没有清理浏览器，现补齐同调用线程的关闭。旧“重启”测试原本留下第一服务运行，已改为真实先退出；并保留新测试专门验证两个存活服务不能被当成重启。测试命令一次误用了不存在的模块名，另有 Windows CRLF 和网页选择器不符，均在记录中区分为验收脚本问题，不以修改产品行为掩盖。

同一设备、同一文件系统上的 OS 锁不等于跨设备账号配额或多人权限。三站真实登录与完整 JD 仍未认证；本修复提高执行可靠性，不替代原访问约束、平台许可或实站验收。当前提交的完整测试和 CI 结果以关联 PR 为准，不自动合并或关闭父 Issue。
