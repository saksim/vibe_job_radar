# 已初始化职位数据库的并发读取

Refs #190 / #188 / #126 / #172。报告分析会重新打开已有Store。旧实现每次都执行`PRAGMA user_version=1`，即使当前版本已经是1，该语句仍会申请写锁。因此，另一个未提交写事务可以阻塞本来可读取已提交WAL快照的报告。

当前仅在原版本为0时写入版本1。原表和索引的`IF NOT EXISTS`补建、WAL、外键、提交行为、30秒数据库等待和后台等待保持。已有记录、观察、事件及旧报告不迁移、不重写；缺失表/索引仍按原规则补建，未知版本继续拒绝。这个改动没有将Store改为只读接口，实际新增记录仍按原事务写入。

未修改源码的人工数据库实验中，普通SELECT能与未提交写事务并存，Store却在重复版本写入时报`database is locked`。六项新增回归的旧版基线有三项失败：读取、版本写权限及完整报告流水线。修复验证同时覆盖版本0升级、当前版本结构补建、未知版本拒绝、已提交记录可见与旧报告保持。

Windows实际程序验收另使用独立人工数据库：一个连接持有未提交写事务，真正exe通过原HTTP接口生成报告，要求条目与此前报告相同；回滚人工写入，重启后继续核对报告。源代码预检与冻结程序资格分开记录，当前提交的独立CI和产物见Issue/PR。

PR189的Windows3.10首轮有一个10秒后台等待失败，失败瞬间堆栈位于Store初始化，但缺少这段等待的完整耗时分解。上述受控复现证明重复元数据写入确实存在，不能据此断言它解释全部历史等待；原首轮工件、唯一同提交复验及#126等未知原因继续保留。不提高时限、关闭fsync、重采真实数据或覆盖旧报告。
