# 已初始化职位数据库的并发读取

Refs #190 / #188 / #126 / #172。报告分析会重新打开已有Store。旧实现每次都执行`PRAGMA user_version=1`，即使当前版本已经是1，该语句仍会申请写锁。因此，另一个未提交写事务可以阻塞本来可读取已提交WAL快照的报告。

当前仅在原版本为0时写入版本1。原表和索引的`IF NOT EXISTS`补建、WAL、外键、已有数据写入事务、30秒数据库等待和后台等待保持。已有记录、观察、事件及旧报告不迁移、不重写；缺失表/索引仍按原规则补建，未知版本继续拒绝。这个改动没有将Store改为只读接口，实际新增记录仍按原事务写入。

未修改源码的人工数据库实验中，普通SELECT能与未提交写事务并存，Store却在重复版本写入时报`database is locked`。六项新增回归的旧版基线有三项失败：读取、版本写权限及完整报告流水线。修复验证同时覆盖版本0升级、当前版本结构补建、未知版本拒绝、已提交记录可见与旧报告保持。

Windows实际程序验收另使用独立人工数据库：一个连接持有未提交写事务，真正exe通过原HTTP接口生成报告，要求条目与此前报告相同；回滚人工写入，重启后继续核对报告。源代码预检与冻结程序资格分开记录，当前提交的独立CI和产物见Issue/PR。

PR189的Windows3.10首轮有一个10秒后台等待失败，失败瞬间堆栈位于Store初始化，但缺少这段等待的完整耗时分解。上述受控复现证明重复元数据写入确实存在，不能据此断言它解释全部历史等待；原首轮工件、唯一同提交复验及#126等未知原因继续保留。不提高时限、关闭fsync、重采真实数据或覆盖旧报告。

## 新数据库的原子初始化

PR196的`4fc7d17`首轮CI又出现Windows3.11与Windows TLS全量回归到15分钟取消，分别保留1958/1931条完成标记。前者更早有四项后台等待断言失败，首个即时线程栈在Store初始化DDL；后者此前没有断言失败标记，取消位置在一个正常节流等待中。[完整首轮证据](https://github.com/saksim/vibe_job_radar/issues/126#issuecomment-5837521382)。这些记录不能证明同一个数据库调用解释了全部耗时。

局部真实SQLite实验另确认：原新库的四条CREATE与版本写入都不在显式事务内，逐条提交；在最后一张表或版本写入失败时，先前创建的表仍留在磁盘。构造函数失败或中断时，尚未进入Store上下文管理器，连接也未关闭。五项初始用例在旧代码有四项失败，原始失败保留。

版本0现在用一个`BEGIN IMMEDIATE`将结构与版本提交；拿到锁后重新检查版本，另一初始化者若已写入未知版本则拒绝并回滚。构造期间任何异常或中断均关闭连接；未提交的新结构一起回滚。版本1仍不额外获取初始化写锁，已有WAL读写并行及结构补建保持。WAL、同步级别FULL、外键及30秒数据库等待均未降低。

六项新增行为用例覆盖结构/版本失败回滚、SQLite异常与KeyboardInterrupt关闭连接、并发初始化版本变化，以及持久化设置和观察外键。既有并行读、版本0升级与完整报告回归继续运行。交替五次的新库实验在本机中位耗时为旧版19.451ms、候选14.952ms，SQL跟踪确认五次结构/版本写入归入同一BEGIN/COMMIT；这是小规模本机证据，不能外推为整个Windows CI超时已解决。
