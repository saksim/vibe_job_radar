# 本地原生浏览器代理的连接接收容量

原生浏览器通过程序自有的回环 CONNECT 代理连接经过验证的目标，TLS 仍由浏览器与目标建立。代理原先继承 Python TCPServer 的默认监听队列 5，独立的活动处理上限为 16。浏览器短时同时发起连接而接收线程尚未获得调度时，队列可能先满，尚未进入处理程序的连接也不会写入 guard.last_error。

现在在绑定监听前明确设置队列容量 16，原活动处理信号量仍为 16。没有更改认证、目标验证、代理选路、TLS、网站限额、请求重试、任务时限或页面断言。超过活动处理容量的连接继续关闭，未认证连接仍返回 407，不能访问上游。

回归使用真实回环 TCP：在明确的接收门闩关闭时发起 8 个连接，再打开门闩并核对认证拒绝与零上游访问；另一用例占满 16 个处理线程，检查第 17 个连接关闭且未进入处理。没有浏览器、系统证书或外部网络。旧实现是负对照，不能仅以新实现通过代替。

本机 Windows / Python 3.12 的一次对照中，原队列只完成 5/8 个 TCP 建连，另 3 个在测试的 2 秒观察内未完成；在启动前设置容量 16 时，8/8 完成且均收到 407。首次尝试在已开始监听后再次调用 listen(16) 没有改变本机结果，该实验也保留。测试观察期限不是产品超时，未增加产品超时。

这只证明可复现的容量缺口，**不证明 #263 或 #178 原 CI 的全部根因**。#178 d1be73f 的首次 24/25、run37190808074/job111402383242/attempt1 保留：搜索 mismatch 用例的预检出现 ERR_PROXY_CONNECTION_FAILED，错误前线程存活、未清理、4 个成功 CONNECT、8 个活动 socket，缺少当时内核队列与底层 socket 错误，不能认定原失败就是队列已满。#263 的其他原始连接失败同样继续开放。

CI 失败事实额外记录纯数字 guard_listener_backlog，以便区分当前配置，不能据此反推出内核排队长度。现有 PR143 的真实驱动关闭类型能力断言与弹窗拒绝计数也恢复到原生验收：没有自然发生的回调异常时计数可为空，不能伪称已实测触发该分支。

参考：[Python socketserver 监听队列说明](https://docs.python.org/3.12/library/socketserver.html#socketserver.TCPServer.request_queue_size)、[Chromium 代理错误说明](https://chromium.googlesource.com/chromium/src/+/HEAD/net/docs/proxy.md)。
