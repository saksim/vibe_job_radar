# 本机 Chrome 的两种采集检查

Refs #50、#63、#205；控制与节奏部分来自旧 #196，经当前主干独立移植。

用户日常 Chrome 能打开登录页面，不代表程序所用的 SDK 启动路径已经通过。本机 Chrome 156.0.8072.0 / Playwright 1.63.0 的默认桥和原SDK原生路径首次都在启动出现0xC0000374；这条失败保留，不宣称其底层堆损坏原因已经修复。旧直接控制方案在本机 Edge154启动也失败，所以这次仅对**明确选择 Chrome 的原生实验**使用新管道控制。配套 Chromium 与 Edge保留现有SDK启动和请求处理路径，无失败后自动改道。

工作台第1步可明确选择本机 Chrome，分别检查默认浏览器桥、原生实验。通过哪一种就只说明该模式的组件检查通过。记录保留所选浏览器及检查模式，服务重启后历史成功不是当前就绪；失败检查不会替换原选择。任务仍由第2步明确选择后端和确认采集。账号、条款、滑块及短信沿用现有人工交接，不读取日常浏览器资料。

Chrome原生只启动新的独立临时会话，控制通道为继承管道；没有远程调试TCP监听、不附着日常浏览器、不改变自动化标记。只调用实际DOM读取和正常输入所需的接口，不启用全局Runtime事件监听，不覆写网页函数、浏览器安全机制或站点策略。当前请求许可、robots、域名、会话所有权、限流和Cookie范围继续生效。文档附加限制保留网站原有CSP，并阻止不受支持的窗口、框架和worker。

独立控制的回调不能在请求间隔里睡眠。因此Chrome原生把已经验证的请求保持暂停，按原共享账本放行，每个请求仅计数和继续一次；等待期间浏览器回复仍可处理。队列最多128项、元数据1MB，原请求/发布者间隔与等待截止不变。重新检查取消、策略、认证和robots；页面退役或导航丢弃旧请求。不保存请求头、口令或请求体。当前SDK路径的原处理体保留。

组件检查验证实际控制器类型、空白页、未许可请求本地拒绝、零外连及清理。Chrome还要求管道桥进程退出、临时资料目录删除且无清理错误，不能仅凭浏览器断开判成功。默认无界面检查和显式可见检查都不访问招聘站点。开发CLI为 --native-browser-check，可配 --native-browser-channel bundled|msedge|chrome；该模式不打开工作区或HTTP服务。Windows候选包须在实际exe内分别检查bundled与Chrome，保留原有五项运行验收，并逐文件校验CDP桥脚本和包内所有文件。CI需要已安装Chrome，不安装或覆盖系统浏览器。

当前隔离原型证据：Chrome156原生组件和保留SDK的Edge154组件通过；Chrome17项密码/短信入口场景、7项本地工作台选择/重启/模式边界、201项相关回归通过。相同两个模拟时钟场景，旧同步等待1失败1错误，排队修复全部通过且20次请求保留0.5秒间隔。原打包元数据缺失和本地验收包装脚本错误均分别记录；它们不改写任何CI结果。

工程验收须新增独立Chrome界面作业和两种模式的原生TLS夹具作业，保留原Edge/Chromium作业。完整JD、原报告、迟到进度状态、有限重试和代理认证必须由这些隔离作业及当前源码/实际exe共同核验。测试CA只允许CI隔离机器，个人主机不安装。上述组件/合成场景不等于实站登录、验证码、真实JD链路或整个旧PR196已完成；准确候选和合并后主干的首次结果以关联PR为准。
