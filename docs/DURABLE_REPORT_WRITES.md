# 报告文件的有界并行持久化

关联 #126 和 PR196。原报告先在私有临时目录逐个生成29个独立文件，每份文件均 flush、fsync、原子替换，再写清单并一次公布报告目录。磁盘等待会沿这29份输出串行累加。PR196 的7a28027虽然四组原生TLS/CORS和浏览器端到端流程通过，Windows便携源码资格仍在旧登录回接测试的5秒报告等待处失败；另一组Windows3.10公开任务的10秒等待也失败。后续读取原进度工件，确认后者失败瞬间同样位于utils.py的fsync，经pipeline.analyze/public_tasks._import；仍不能仅凭瞬间堆栈解释全部耗时。19/21的原结果及两个首次失败继续保留，没有重跑工作流。

现将这些独立输出交给最多4个写入线程。抽取、统计、权限、数据选择和网络流程不并行；每个文件仍调用原atomic_text/write_csv及真实fsync。清单的计算和持久化在全部输出成功之后，最后仍由原子目录替换公布。任一输出失败会取消尚未启动的写入，并等已运行线程退出后清理私有目录；失败不会产生可见的半份报告，也不覆盖旧报告。线程数固定，不能由网页或配置扩大。

## 已完成的验证

- 同一固定合成数据库、相同分析时间下，修复前后30个文件（含最终清单）逐字节一致，所有输出哈希有效。
- 对原登录回接测试附加每次180毫秒的人工磁盘延迟，原串行源码在原5秒等待处失败。相同延迟、原fsync和原断言下，修正后完成测试；观测最多4个同时持久化，清理后没有活动写入。两个完整测试运行经过的步骤不同，不把总耗时差当作性能倍数。
- 实际文件测试覆盖四线程上限、每份输出完成持久化才写清单、导出失败等待其他写入后清理、清单失败、最终目录提交失败和原报告保留。
- 旧测试的持久化观察器现在同时计入该任务的报告写入线程，不计入其他任务。累计fsync时间可能重叠，不能相加冒充经过的墙钟时间；进行中耗时为最长尚未完成调用。

这些对照证明串行磁盘等待是可复现的一种瓶颈，并验证本改动的完整性，不证明所有旧CI失败同因。没有扩大5/10秒测试等待或资格时限、减少输出文件、取消持久化或重算用户真实报告。当前提交的完整回归、跨平台CI和实际程序资格另行记录；猎聘正常搜索、本人登录与真实JD链路仍须实测。

## 后续：精确本批副本使用内存数据库

`2fb831e` 的首次 CI 最终为16/21。四组原生失败是验收脚本的线程归属错误；Windows便携源码资格另在600秒上限停止，已开始1686项、完成1685项，exe尚未构建。此前四个旧登录回接测试在5秒等待处失败，瞬时栈包括临时批次数据库建表、Store.add和四个报告fsync线程。原进度与首次失败保留；不能用这几份栈推定所有超时同因，或把总超时归因于最后尚未结束的测试。

guided与公开来源任务已先将正文持久化到原始库。原实现随后又建临时SQLite文件、复制当前批次，关闭后重新打开，只为排除其他批次。现在这份临时副本使用独立内存Store，继续沿用相同SQLite快照选择、历史排序和去重语义；analyze可以借用调用方拥有的Store，成功或失败都不关闭它。调用方在报告生成后关闭内存副本，原路径输入仍自行打开/关闭数据库。

原始正文保存、精确本批范围、输出内容、报告29份文件及清单的fsync/原子发布、错误清理和5/10/600秒限额保持。测试覆盖两种输入的30份文件逐字节等价、读/导出失败后的连接所有权和清理，以及两条实际任务链在临时磁盘数据库不可用时仍只报告当前批次并保留原库其他记录。这避免已定位的重复数据库磁盘等待，不能保证任意慢盘都满足原时限；新提交完整回归和CI结果另行记录。
